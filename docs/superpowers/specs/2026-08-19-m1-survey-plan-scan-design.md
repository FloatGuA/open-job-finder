# m1 重构：探结构 → 定桶计划 → 逐桶扫

**日期**：2026-08-19
**状态**：设计定稿，待写实现计划
**触发**：join.qq.com 四轮真机全部 found=0。前三轮死在上下文裁剪把点击反馈删掉（已修，v2.27.1）；
第四轮循环消失、筛选器生效（岗位 940 → 243），但 `record_job` 一次没调——它看着 243 个岗位
还在纠结要不要再细分筛选。

---

## 1. 为什么要改

### 1.1 直接原因：一个巨大的 ReAct 节点承担了性质完全不同的三件事

现在 `find_jobs` 是**一个** ReAct 循环，里面混着：

1. 摸清这个站怎么组织（探索，需要试探和回读）
2. 决定打哪几个桶（纯判断，不碰浏览器）
3. 逐条读岗位、判类别、落袋（机械 + 判断混在一起）

三件事共享一个步数预算、一个上下文、一个完成判据。表现是：**一段跑飞就把整轮预算吃光**，
而且前端只能看到"find_jobs 卡住了"，看不出卡在哪一段。

### 1.2 更深的原因：`max` 一个数字兼三职

`profile.yaml` 的 `job_seeking.categories[].max` 同时是：

- **导航信号**——`record_job` 在该类满额时拒绝记录，全满则通知 agent 收尾
- **最终交付量**——Checkpoint 1 上你看到的就是这几个
- **隐含的阅读上限**——满了就不再往下看

第三条从没被显式设计过，却是最有后果的一条：**根本不存在"候选"这个概念，找到的即是最终的**。
开发那 5 个一满，第 4 页更好的开发岗永远不会进入视野，**而且事后无从知道错过了什么**，
因为它压根没被读过。

### 1.3 附带原因：几乎无法本地迭代

m1 的逻辑几乎全部埋在 ReAct 循环里，要真浏览器 + 真 LLM 才跑得起来。唯一测得到的那块
（上下文裁剪）用了不真实的桩（`"SNAPSHOT-1"` 当快照），所以 2026-08-19 那个把点击结果整段
删掉的 bug 从单测里溜了过去。**改 prompt 要等 4 分钟真机跑，还未必可复现。**

## 2. 新的 m1 形状

```
ensure_ready        代码       导航 + 等渲染 + 等登录（不变）
      ↓
survey_structure    ReAct      看懂这个站怎么分桶。**允许试探筛选器**。
      ↓ 站点手册（state + 持久化）
plan_buckets        LLM 调用   对着手册 + 求职条件，定打哪几个桶、什么顺序
      ↓ 桶计划
scan_buckets        ReAct      逐桶切换 + 调 harvest 工具
      ↓
write_pending_jobs  代码       落库（不变）
```

`M1_STAGES` 相应变为
`("ensure_ready", "survey_structure", "plan_buckets", "scan_buckets", "write_pending_jobs")`。
前端第 2 层骨架**从图定义导出**，无需手改。

### 2.1 为什么 `plan_buckets` 不是 ReAct

它不碰浏览器：输入是手册和求职条件，输出是一份桶清单。没有「观察 → 行动」的循环可言。
做成普通 `build_model()` 调用的好处是**可单测、可做 eval**（给定手册 A + 条件 B → 该选哪些桶，
有 ground truth），而 ReAct 循环基本没法这么测。

整个 m1 里 ReAct 只剩两处，都在真正需要"看一眼再决定下一步"的地方。

### 2.2 否掉的方案

- **否掉「拆成独立的勘察 agent + 选岗 agent」**（本设计的第一版）。理由：「哪些桶跟我相关」
  是**目标依赖**的判断，不是中性的站点知识；一个不知道目标的勘察 agent 只能产出泛泛的站点
  说明，选岗那段还得把映射重推一遍。而且勾筛选器和读岗位在真实操作里是**交织**的。
  第四轮真机已经证明这个 agent 自己就能把筛选做对——那部分它本来就会。
- **否掉「不加节点，只加工具 + 改 prompt」**。理由：没有阶段级的预算隔离和完成判据，
  前端也看不出卡在哪一步。
- **否掉把 `set_hard_filters` 单列为一个节点**。理由：地点跟岗位类别一样是个筛选维度，
  单拎出来等于假设"有些条件不分桶"，而那只是某一个站的形状。

## 3. 站点手册

### 3.1 它是什么

`survey_structure` 的产出，**节点之间的接口**，同时持久化供下轮轻校验。

**关键约束：手册的每个字段只能从一组我们实现了执行器的取值里挑。** 手册要被代码执行，
所以不能是散文。这组原语就是"通用性"的预算所在——**遇到新站的正确反应是加一个执行器
（一次，全站通用），而不是给某个站打 prompt 补丁**。

### 3.2 Schema（首版）

| 字段 | 取值 | 说明 |
|---|---|---|
| `job_url_source` | `link_in_row` / `new_tab_on_click` / `id_template` | 岗位 URL 怎么拿 |
| `url_template` | 字符串，可空 | 仅 `id_template` 用 |
| `pagination` | `next_button` / `url_param` / `infinite_scroll` / `none` | 怎么翻页 |
| `filter_interaction` | `direct_click` / `expand_group_then_click` | 筛选选项要不要先展开分组 |
| `filters_survive_reload` | bool | 重新导航能不能重置筛选（见 §7） |
| `total_count_locator` | 字符串，可空 | 计数文本的**正则**，须含一个数字捕获组（如 `共(\d+)个岗位`）。空＝这个站没有计数，则 §3.3 的试探判定退化为「对比列表行数」，可靠性下降，手册需在 `notes` 里注明 |
| `row_split` | `anchor_text`（已实现）/ `container_per_row`（**声明未实现**）| 列表怎么切成一行一行，见 §3.7。未实现的取值由 `from_dict` 拒绝——闭集的意义是「过了校验就代表代码能执行」，否则它会被写进 survey prompt、然后在运行中途崩溃，绕开 §7 那个「所有执行器都不匹配就诚实报搞不定」的出口 |
| `row_anchor` | 字符串 | 仅 `anchor_text` 用：每个岗位行里必现且仅现一次的文本 |
| `dimensions` | 列表 | 每个筛选维度：`name` / `options[]` / `multi_select`(bool) |
| `important_notes` | 自由文本 | **超出手册设计预期的一切**。留空是常态，见 §3.6 |

### 3.6 `important_notes`：超出预期的一切都往这里放

**每一条非空记录，都是一句「现实超出了我们的模型」**——这是整个设计里信息密度最高的信号，
也最容易烂掉。按本项目的文档判据：**没有读者的东西必然烂掉**，所以它需要一个会被真的读到
的位置和一个会让人停下来的名字。

**刻意不拆成「无害笔记」和「能力缺口」两格。** 拆分要求 agent 先判断自己这条观察属于哪一类，
而**那个判断本身就是它会做错的事**——一旦把真缺口误标成无害笔记，缺口就从待办里消失了，
且没有任何东西会发现。合成一格，全部浮上来，人多看一眼的成本远低于漏掉一条的成本。

（代价是失去按类型跨站点聚合"三个站都卡在同一个缺口上"。目前总共两个站，那种聚合要到
七八个站才开始有价值——过早设计，等真需要时再从这一格里提炼。）

**护栏：留空是常态，写了就是异常。** 强提醒最容易死在这里——如果 agent 每轮都往里写点什么
（"这个站有筛选器"），`important` 三个字在第三轮之后就退化成噪音，跟没有一样。
**prompt 必须明说：§3.2 那几格装得下的，一律不要写进来。**

**配套：`survey_structure` 报"搞不定"时必须在这里写明缺什么。** 不许只说"这个站我搞不定"
——一句没有缺口描述的失败，跟随便一次失败没有区别。

**前端**：手册视图里这一格非空就显眼呈现（橙色），不折叠、不截断。

### 3.7 行切分：按锚点切，点锚点取 URL

**问题**：有的站的岗位卡片在 a11y 快照里没有容器节点，整页是一串平铺的 `StaticText`
（join.qq.com 就是），"哪几个节点属于同一个岗位"没有结构可依。

**解法（已真机验证）**：手册给一个 `row_anchor`——每个岗位行里**必现且仅现一次**的文本。
join.qq.com 上是 `工作地点：`，列表区里恰好出现 10 次，对应 10 个岗位；锚点 uid
`1_78 / 1_87 / 1_96 / 1_105` 等距分布（周期 9）。

**关键验证**：`click` 锚点节点本身，会打开**它所在那一行**的岗位详情页——事件冒泡到卡片的
`onClick`。实测点 `1_87`（"Agent开发工程师"卡片里的锚点）得到
`postid=1282707395466077184`，与第一个岗位的 `...398326592512` 不同，确实是它自己那一行。

由此：

- **取 URL 直接点锚点**，不需要定位标题节点
- **不需要精确切出标题**——每段的原始文本整个交给分类 LLM，它本来就要读这一段才能分类，
  顺便读出标题是免费的
- 行数 = 锚点数，这个数字同时是 harvest 的进度分母

避开的坑：列表区开头往往夹着推广文案（本站是「不确定适合哪个岗位？…」三条），
按"第一个文本节点即标题"会直接抓错。


### 3.3 多选还是互斥，只能靠试探

**a11y 快照给不了这个信息。** 对 join.qq.com 的实测（`logs/joinqq_snapshot.txt`，6613 字符）：

| 想知道的 | 快照里有没有 |
|---|---|
| role 是 checkbox 还是 radio | ✅ 有 |
| **某个框勾上了没有** | ❌ **整张快照 0 处 `checked`** |
| 互斥分组的边界 | ❌ radio group 在 chrome-devtools-mcp 里没有包裹节点（PITFALLS 已记） |
| 跨维度是 AND 还是 OR | ❌ 无 |

第二行追认解释了第四轮的怪现象：它反复写 "None of them seem to be selected/checked yet"
——**它说的是实话**，快照里真的没有勾选状态，它点完之后无从确认。它在一个**没有反馈的动作**
上反复找证据，跟上下文裁剪那个 bug 是同一个病：**动作做了，结果看不见。**

**唯一可靠的判定方式是「试一次 + 回读总数」**：`共940个岗位` → 勾一个 → `共243个岗位`。
这个计数便宜、可靠、招聘站基本都有，`total_count_locator` 就是为它留的。

因此 `survey_structure` **必须允许动筛选器**。

### 3.4 试探之后怎么收场

**节点结束时由代码重新 `navigate_page` 到入口页**，得到确定的干净状态。
**不依赖 agent 自己撤销**——快照不报 `checked`，它无从确认自己恢复没恢复，
那正是我们刚踩完的"动作做了但看不见结果"那类坏味道。

### 3.5 持久化与轻校验

存 `site_manuals` 表（`site_name` 主键 + `manual` JSON + `updated_at`），与现有 `site_briefs`
**并存、职责分开**：

- **手册**＝本轮可执行的事实，结构化，代码消费
- **brief**＝跨轮经验笔记，自由文本，喂进 prompt 给人（模型）看，明确标注可能过期

下一轮 `survey_structure` 拿到旧手册后只做**轻校验**，过了就直接进 `plan_buckets`，
不过就整份丢弃重探。**不做"部分沿用"——一份半对的手册比没有更糟。**

**「验过了」的判据是这三条全部成立**（写死，不留给实现时发挥）：

1. **计数文本仍在**——按 `total_count_locator` 能在入口页快照里找到一个含数字的文本节点
2. **第一个维度的选项没有消失**——`dimensions[0].options` 里的每一项都还能在本次快照里找到

   > **它检测不到「新增了选项」，这是刻意接受的**（2026-08-19 实现时确认）。
   >
   > 原因是**当前实现**拿整份快照的所有节点文本做 `have` 集合（导航栏、岗位标题都在内），
   > 所以反向差集 `have - want` 会 100% 命中、让校验永远失败、持久化形同虚设。
   >
   > **注意这不是"结构上做不到"**——最终评审纠正过这一点：本站的 tab 节点自带
   > `description="应届毕业生 checkbox-group 实习生 checkbox-group …"`，**分组成员就写在
   > 父节点的 description 属性里**，只是 `_NODE_RE` 目前把 `description` 丢了；
   > 另有更便宜的一档：按 role 过滤 checkbox/radio 节点（role 已经在正则里捕获了）。
   > 计划 B 有这两条路可走，**不要因为这段话就跳到更弱的"记选项个数"兜底**。
   > 代价对比：漏检新增＝**少扫**一个新分桶（可恢复，且人在 Checkpoint 1 看得到全部候选）；
   > 强行双向＝每轮白付一次全量重探。后者严重得多。
   > **留给计划 B（按优先级）**：① 让 `_NODE_RE` 保留 `description`，从父 tab 节点直接读分组成员；
   > ② 或按 role 过滤把 `have` 限定到 checkbox/radio；③ 实在不行才退到"记选项个数"。
3. **取 URL 的方式仍然成立**——按 `job_url_source` 对**第一个岗位**实取一次 URL，
   拿到合法 http(s) 链接才算过

三条都是**读+一次实取**，成本约 3–5 步，远低于全量重探。任一条不过即整份作废。

## 4. 候选上限与名额：一个数字拆成两个

| | 现在 | 新设计 |
|---|---|---|
| 抓多少个来看 | 没有这个概念（＝ `max`） | **`candidates_per_bucket`**——决定取多少份 JD ＝ 决定 run 多长 |
| 最终给你多少 | `max` | 评分排序后按类别呈现，**不再影响抓取** |

`candidates_per_bucket` 落在 `profile.yaml` 的 `job_seeking`（与 `categories` 同源，
都是"我要找什么"），前端设置页可调。

「过早填满丢掉更好的」因此消失：**排序发生在全部候选都拿到 JD 之后**。
这同时完成路线图的 ④（名额与评分）和 ⑤（前端调阈值）。

> 术语区分（实现时别混）：**桶**＝站点自己的顶层分类（技术/产品/设计…），运行时发现；
> **类别**＝我们的目标类别（AI NATIVE/开发/产品…），来自 profile。桶计划做的就是这两者的映射。

## 5. `harvest_current_page`：agent 手里的工具，不是节点

```
harvest_current_page(bucket)          ← scan_buckets 的 agent 调用，代码执行
  1. 解析当前列表页 → N 行（标题、站点类别、地点…）
  2. 按 job_url_source 逐行取 URL
       link_in_row      → 行里就有，零成本
       new_tab_on_click → 点开 → list_pages 读 URL → **顺手读 JD** → close_page
       id_template      → 拼 URL → 导航读 JD
  3. 批量交 LLM 分类（标题 + 站点类别 + JD）
  4. 落袋，返回各类进度
```

分工：**agent 决定去哪个桶、勾哪个框、还要不要继续**（真判断）；**代码承担"把这一页 N 条
抓下来"**（机械且昂贵）；**分类是 LLM，但批量、不占 ReAct 轮次**。

这也解开 `record_job` 现在的死结——它要求 agent 提供一个屏幕上根本不存在的 URL，
错误提示还指着 `url="..."`（那是某个站的形状被写进了工具契约）。

### 5.1 JD 总是取，不猜

**否掉「两遍分类 + `needs_jd` 标记」**：LLM 自报置信度不可靠，它很可能对着一个含糊标题
信心满满。

成本上这个决定比看起来便宜：**在 `new_tab_on_click` 类站点上，「取 URL」和「取 JD」是
同一次访问**——本来就必须点开详情页才能拿到 URL，顺手读 JD 近乎免费。

单个岗位一次详情页往返保守估 6–10 秒，所以 run 时长 ≈ `候选总数 × 8 秒`。
`candidates_per_bucket` 就是这个旋钮。

### 5.2 JD 要落库

`pending_jobs` 加一列（或侧表）。三个确定的消费方：

1. **④ 的评分**——W1 的评分器吃的就是 JD，抓一次两处用
2. **审批页**——Checkpoint 1 上看得到 JD 才好判断
3. **eval**——路线图「阶段2 评分 eval」要攒真实 `scored_jobs`，这条路径天然在攒

### 5.3 JD 的清理：删正文，留骨架

审批完成后（或该站点一轮投递结束后）**删除 JD 正文，保留 `pending_jobs` 的骨架**
（url / title / category / status）。

- 体积：一条不含 JD 的记录约 200 字节，JD 通常 2–5KB——**删正文即消掉 95% 以上的体积**，
  1000 个岗位的骨架也只有约 200KB。
- **骨架不能删**：`known_urls` 去重的唯一依据就是它。整条删掉之后，下轮重跑同一个站会把
  **已经投过的岗位当成新岗位重新排队**——你要重审一次，m2 会再传一次简历，m3 会再投一次。
  本项目已明确记过「重复排队 = 再对同一家公司传一次简历」这个风险。

> 没有 JD 时分类只能靠标题 + 站点自带类别，而 prompt 里最核心的那条归类规则
> （「职责里出现 LLM/Agent 就归 AI NATIVE，哪怕标题像普通研发岗」）**一个字都执行不了**。
> 真实误判有案可查：「数据算法工程师」职责写着 CV/多模态/LLM/Agent，被归成「开发」，
> 还占掉开发最后一个名额把 AI NATIVE 饿死。根因是**它当时就没有足够信息，却被迫给了答案**。

## 6. Prompt 作为可编辑资产

三段各自独立的 `.md`，全部加进 `services/prompt_manager.EDITABLE_PROMPTS`：

- `layer1_survey_structure`
- `layer1_plan_buckets`
- `layer1_scan_buckets`

`/api/prompts` 遍历 `EDITABLE_PROMPTS`，Settings 页 `prompts.map(...)` 自动列出——
**加名字即接线，前端零改动**。现有的占位符校验（编辑后 `{{...}}` 集合必须与默认一致）
自动生效，防止改坏。

顺带把仍然存在的 `layer1_open_application` 等 m2 prompt 一并加入——它们同样只能靠改文件
才能调，这个缺口不该只补一半。

## 7. 失败模式

每条都要有个**不会被误读成"正常"**的出口。

| 情形 | 处理 |
|---|---|
| 所有执行器都不匹配这个站 | `survey_structure` **诚实报"搞不定"并终止**，绝不硬填最接近的。硬填的后果是 harvest 抓回垃圾，**而那看起来跟"站上没岗位"一模一样** |
| 轻校验失败（站点改版） | 整份丢弃重探，不部分沿用 |
| `filters_survive_reload=true` | 手册里记着；改用逐个取消，取消不掉就报搞不定 |
| 单个岗位取 JD 失败 | 跳过并计数，**不中断整页**；结果标注"N 条取 JD 失败" |
| 步数耗尽 | 已有机制：`partial` + 黄色 + 「名额没满的类别可能只是没扫到」 |
| 分类 LLM 挂了 | 整页回退，**不写库**。半页落库会让下次去重误判成"已收录" |

---

## 8. 可测性（本设计最大的附带收益）

| 部件 | 怎么测 |
|---|---|
| 手册的每个执行器（取 URL / 翻页 / 筛选交互） | 单测，喂真实快照 fixture |
| harvest 的列表解析 | 单测，喂真实快照 fixture |
| `plan_buckets` | **可 eval**：给定手册 + 条件 → 该选哪些桶，有 ground truth |
| 分类 | **可 eval**，且 JD 落库后天然在攒真实样本 |
| `survey_structure` / `scan_buckets` | 只能真机——**但只剩这两段** |

**fixture 必须用真实尺寸的快照**。2026-08-19 的教训：旧裁剪测试拿 `"SNAPSHOT-1"`
（10 字符）当快照，在一个真实世界里不存在的输入上做断言，于是那个把点击结果整段删掉的
bug 从单测里溜了过去。真实快照 6613 字符、点击返回 114/206——**这个数量级差正是判据本身**。

## 9. 明确不做

- **不引入外层图的条件边**（「选岗发现手册错了 → 回到勘察」）。现在是纯线性，
  条件边会带来"探→选→探→选"的新循环风险。手册错了本轮就失败，下轮重探。
- **不给 Layer 1 开 `evaluate_script` / `fill` / `type_text` / `press_key`**。
  白名单只加过标签页三件套（不可能提交表单）。读列表 API 那条路要动安全边界，**单独立项**。
- **不做跨 run 的岗位状态机**（m1 run / 人工审批 / m2 run 用 `pending_job_id` 串起来）。
  那是 m1/m2/m3 拆图那条线的事。
- **不让 agent 自己写执行器代码**（即"自进化"）。技术上不遥远——前提是它能验证自己写的东西，
  而本设计 §8 建的正是那套基建。**明确不走，理由不是技术**：这个系统能操作真实浏览器、能对
  真实企业投简历，它的安全边界建立在**"不给能力"**上（白名单挡住 `evaluate_script`，提交动作
  代码硬拦）。**让它自动往自己身上加执行器，正好是把这条边界反过来。** 收益是省几小时写代码，
  风险是一个能自我扩权、且会产生不可撤销对外动作的系统——不成比例。
  `important_notes`（§3.6）是这条路上刻意停下的位置：**agent 发现并上报，人来补**。

## 10. 已拍板结论（回填 DECISION.md）

1. 勘察产出**结构化站点手册**，不是自由笔记——下游要用代码消费它。
2. **不拆成两个独立 agent**：探结构是选岗任务的前半段，不是独立任务。改为一个任务、三个图节点。
3. 手册**持久化 + 每轮轻校验**，不做部分沿用。
4. 选岗分工＝**代码批量抓 + LLM 批量分类**；agent 只管导航与桶策略。
5. `survey_structure` **允许试探筛选器**，结束后由**代码重新导航**重置。
6. **总是取 JD，不猜**——否掉 LLM 自报 `needs_jd`。
7. 候选上限**按桶设、前端可调**；`max` 退化为呈现上限。
8. `plan_buckets` **不做成 ReAct**——它不碰浏览器，做成普通 LLM 调用换来可测性。
9. 手册只留**一格** `important_notes` 装"超出预期的一切"，**刻意不拆**成笔记/缺口两类——
   拆分要求 agent 自己分类，而误分类会让真缺口静默消失。护栏是「留空是常态」。
10. **不让 agent 自己写执行器**（自进化）。安全边界建立在"不给能力"上，自动扩权正好反过来。
    停在「agent 发现并上报，人来补」这个位置是刻意的。
11. JD **审完删正文、留骨架**——骨架是去重的唯一依据，整条删会导致重复投递。
